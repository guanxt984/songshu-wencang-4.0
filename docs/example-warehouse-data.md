# 范例一：《如何成为产品经理》

## 一、用户上传的原始松果

- **A01**：先理解问题，再讨论功能。
- **A02**：产品经理的职责不是替所有人做决定，而是让团队围绕同一个用户问题、目标和判断标准做决定。
- **A03**：项目复盘要写清楚三个转折：最初相信什么，后来被什么证据推翻，最终为什么选择现在的方案。只有最终页面和上线结果，看不出产品经理真正做过的判断。
- **A04**：访谈时少问“你想要什么功能”，多问“上一次遇到这个问题是什么时候”。
- **A05**：尽早拿半成品给真实用户使用。
- **A06**：用户提出的方案不是需求本身。例如用户说“加一个导出按钮”，真正的问题可能是他需要把结果交给没有系统账号的同事。先追问使用对象、交付格式、发生频率和现有替代方法，再决定是否真的需要按钮。
- **A07**：上线不是终点。至少要观察目标用户是否使用、核心任务是否完成、失败集中在哪一步，以及新功能有没有制造额外负担。
- **A08**：体验竞品时不要只截图页面。按完整任务走一遍，记录入口是否容易发现、第一次操作是否需要学习、系统怎样反馈结果、失败后能否恢复、哪些设计只是因为它的业务条件与自己不同。
- **A09**：每个页面只保留一个最重要的下一步。
- **A10**：面试讲项目时，先用一句话交代用户、问题和结果，再展开自己的判断过程。不要从项目背景讲五分钟后，面试官还不知道你解决了什么。
- **A11**：用户说“挺好的”不等于需求成立。观察他是否愿意改变原来的做法、投入时间、提供数据或持续回来使用，比礼貌性的肯定更可靠。
- **A12**：产品经理交付的不是需求文档，而是被团队共同理解并最终产生用户价值的解决方案。
- **A13**：不会技术细节时可以请教，但必须能把业务目标翻译成边界、输入、输出、异常情况和验收标准。
- **A14**：先解决高频、刚需、路径明确的主场景。
- **A15**：需求优先级不能只看谁声音大。可以同时比较影响人数、发生频率、问题严重程度、战略价值、验证成本和机会窗口；结论不必依赖复杂公式，但必须让团队知道为什么现在做它而不是另一个。
- **A16**：写需求前先画出现有流程。用户在哪里开始、需要哪些信息、经过谁、等待多久、在哪些地方返工，通常比一开始画新页面更容易暴露真正问题。
- **A17**：异常流程也是产品体验。
- **A18**：求职时从目标岗位中提取反复出现的能力要求，再为每项能力准备证据。写“熟悉用户研究”不如写清楚访谈了谁、改变了哪个判断、最终减少了什么风险。
- **A19**：产品经理不必成为每个岗位的专家，但要知道该在什么时候让设计、研发、运营、销售、法务或客服参与，不能等方案确定后才通知相关角色承担后果。
- **A20**：好产品会让用户自然知道下一步，而不是依靠大段说明告诉他怎么用。
- **A21**：测试用例不能只有正常路径。还要覆盖空数据、重复提交、权限不足、网络中断、输入错误、多人同时修改和用户中途退出，因为用户对产品可靠性的判断往往来自这些边缘时刻。
- **A22**：对高风险操作提供确认、撤销和记录；对低风险高频操作减少打断。安全感不是到处弹确认框，而是让保护强度与错误代价匹配。
- **A23**：写项目经历时少用“负责、协助、跟进”，多写发现了什么矛盾、选择了什么方案、放弃了什么、如何验证，以及结果说明了什么。
- **A24**：用最低成本验证最不确定的假设。如果最大风险是用户根本不需要，就先验证需求；如果风险是流程跑不通，就先做人工服务或可点击原型，不必急着开发完整系统。
- **A25**：数据分析先从问题开始。与其漫无目的地看几十张报表，不如先提出“新用户为什么没有完成第一次关键行为”，再选择分群、漏斗、路径和访谈去寻找答案。
- **A26**：指标必须配对看。转化率提高可能伴随退款增加，使用时长增长可能源于流程变慢，消息发送量上升也可能是用户反复询问仍没解决问题。
- **A27**：减少用户输入。
- **A28**：战略不是罗列想做的事情，而是明确服务谁、解决什么核心问题、依靠什么优势，以及现阶段主动不做什么。没有取舍的路线图只是需求集合。
- **A29**：计算功能价值时同时考虑开发、维护、客服、培训和用户迁移成本。一个容易上线却长期需要人工补救的功能，真实成本可能远高于最初估算。
- **A30**：方案评审前准备三个版本：理想方案、能验证核心价值的最小方案，以及时间或资源继续收缩时仍可交付的底线方案。这样团队讨论的是取舍，而不是在会上临时删功能。
- **A31**：产品判断可以错，但假设必须说清楚。
- **A32**：需求文档至少说明目标用户、使用场景、要解决的问题、成功标准、核心流程、关键规则、异常状态、数据需求和不在本期处理的范围。文档的目的不是显得完整，而是减少不同角色对同一方案的不同理解。
- **A33**：产品经理要对结果负责，但不要把“负责”误解为控制所有过程。真正有效的方式是公开信息、明确负责人和截止条件，让问题尽早暴露，而不是自己接住所有任务。
- **A34**：学习产品最有效的方法之一，是选一个每天使用的产品，持续拆解它的目标用户、核心任务、商业约束、信息结构和关键取舍，再尝试为一个真实问题提出更好的方案。
- **A35**：五个目标用户的真实使用记录，通常比五十个朋友在群里说“这个想法不错”更有价值。前者能暴露理解偏差和流程障碍，后者往往只是对创意的礼貌回应。
- **A36**：界面更简洁不等于任务更容易。隐藏低频但关键的信息、把多个步骤塞进一个按钮、为了视觉干净取消状态提示，都可能让用户承担更多理解成本。
- **A37**：出现意见分歧时，把争论改写成可以验证的问题：双方分别相信什么、需要什么证据才会改变判断、最小验证动作是什么。这样能把职位和表达能力的较量，重新拉回事实。
- **A38**：B 端产品不要只访谈管理者。管理者决定购买，一线人员每天使用，财务、IT 和法务可能决定能否落地，他们面对的目标、成本和风险并不相同。
- **A39**：用户留存下降时，先区分“没有获得价值”“获得价值但不再需要”“使用成本太高”“被替代方案带走”和“产品故障导致流失”，不同原因不能用同一种召回策略处理。
- **A40**：一次完整复盘应包含目标、背景事实、关键假设、方案选择、协作过程、上线结果、用户反馈、数据变化、未解决问题和下一轮判断。复盘不是证明当时做得正确，而是提高下一次决策质量。

## 二、松果架整理结果

### 松果架 1：岗位职责与产品思维（6 颗松果）

- A02：让团队围绕同一个用户问题和判断标准共同决策。
- A12：产品经理交付的是产生用户价值的解决方案，而不只是文档。
- A13：把业务目标翻译成可实现、可验收的产品边界。
- A20：通过自然的流程设计让用户理解下一步。
- A31：允许判断出错，但必须明确提出了什么假设。
- A33：对结果负责不等于控制所有过程。

### 松果架 2：用户研究与问题发现（7 颗松果）

- A01：先理解问题，再讨论功能。
- A04：用最近一次真实经历替代抽象的功能询问。
- A06：把用户提出的方案还原成对象、场景、频率和障碍。
- A11：用行为投入判断需求，而不只听礼貌性的肯定。
- A16：先画出现有流程，从等待和返工中发现问题。
- A35：真实使用记录比泛泛的创意认可更有价值。
- A38：B 端研究需要覆盖购买者、使用者和落地影响者。

### 松果架 3：需求判断与产品策略（7 颗松果）

- A14：先解决高频、刚需、路径明确的主场景。
- A15：综合影响、频率、严重程度、战略价值和成本判断优先级。
- A24：用最低成本验证最不确定的假设。
- A28：战略必须说明服务对象、核心问题、优势和主动取舍。
- A29：评估开发之外的维护、服务和迁移成本。
- A30：用理想、最小和底线三个版本讨论范围取舍。
- A39：先识别留存下降的不同原因，再选择应对策略。

### 松果架 4：方案设计、数据与体验验证（7 颗松果）

- A07：上线后观察真实使用、任务完成和失败位置。
- A09：每个页面突出一个最重要的下一步。
- A17：异常流程同样决定产品体验。
- A21：测试需要覆盖边缘情况和恢复路径。
- A22：确认和撤销的强度要与错误代价匹配。
- A25：带着明确问题选择数据分析方法。
- A26：通过配对指标识别单一指标背后的副作用。

### 松果架 5：项目推进与团队协作（6 颗松果）

- A03：复盘最初判断、证据变化和最终方案之间的关系。
- A05：尽早用半成品获取真实反馈。
- A19：在正确阶段让相关角色参与决策。
- A23：用判断、取舍、验证和结果描述个人贡献。
- A32：用需求文档减少跨角色理解偏差。
- A40：以提高下一次决策质量为目标进行完整复盘。

### 松果架 6：学习、作品集与求职表达（3 颗松果）

- A10：用用户、问题、结果和判断过程讲述项目。
- A18：从岗位要求反推需要准备的能力证据。
- A34：通过持续拆解真实产品训练产品判断。

### 暂存栏（4 颗松果）

- A27：减少用户输入同时涉及交互设计、流程设计和信息获取，暂不限定单一分类。
- A36：界面简洁与任务容易并不等价，横跨交互设计和产品判断。
- A37：把意见分歧改写成可验证问题，同时属于协作方法和验证方法。
- A08：完整体验并记录竞品任务流程，同时适用于产品学习和方案验证，暂不限定单一分类。

# 范例二：《人性的弱点摘抄》

## 一、用户上传的原始松果

- **H01**：少批评，多理解。
- **H02**：每个人最关心的通常还是自己，所以谈话如果一直围绕“我”，对方很快就会失去兴趣。
- **H03**：很多争论从一开始就把目标设错了。双方都在收集证明自己正确的论据，却没有确认事实分歧、利益分歧还是情绪分歧。即使一方在逻辑上获胜，也可能让另一方更坚定地维护原有立场。先判断这场对话是否真的需要输赢，再决定要不要继续争论。
- **H04**：如果必须指出错误，可以先说自己也可能判断不完整，再一起看事实。
- **H05**：记住对方的名字。
- **H06**：书里的商业案例年代很久，但人希望被尊重、被理解这件事没有明显过时。
- **H07**：与人合作时，先问对方想得到什么，不要一上来只解释自己的目标。
- **H08**：真诚赞美要建立在观察上。与其说“你真优秀”，不如指出对方在哪个具体时刻付出了什么努力、这个行动给他人带来了什么帮助。具体的肯定让人知道哪些行为值得继续，也能减少奉承带来的不信任感。
- **H09**：人在被否定时会本能防御，哪怕内心知道对方说得有道理。
- **H10**：今天开会试了一下，先复述对方的顾虑再提方案，对方明显没有那么抵触。
- **H11**：不要直接命令，改成提问，让对方参与决定怎么做。
- **H12**：表情先于语言传递态度。
- **H13**：人喜欢谈论自己熟悉和在意的事情，好的倾听者不必急着展示自己知道多少。
- **H14**：如果希望别人行动，要把事情和他的需要联系起来，而不是只说“这是规定”。
- **H15**：迅速、直接地承认错误。
- **H16**：有时所谓讲道理只是想赢，对解决问题没有帮助。
- **H17**：让对方保全面子不是纵容，而是不给羞耻感阻碍后续改变。
- **H18**：公开批评比私下沟通更容易让人把注意力放在维护身份上。
- **H19**：谈对方感兴趣的话题，不应该变成机械套话，否则很容易让人感到被操纵。
- **H20**：当一个人刚开始改善时，不要只盯着他距离理想标准还有多远。及时指出已经出现的微小进步，说明哪些具体行为产生了积极结果，再给出下一步可以做到的目标。鼓励不是降低标准，而是让改变者看见继续努力的路径。
- **H21**：在谈不同意见前先找共同点，双方至少要知道想解决的是同一件事。
- **H22**：人希望自己的存在和努力被看见。表达认可时，要让对方感到自己真正参与并影响了结果。
- **H23**：如果一个人一直抱怨，直接告诉他“别抱怨了”通常不会有效，先弄清他到底在担心什么。
- **H24**：开放提问，就接受意外答案。
- **H25**：书里很多方法也可能被用来操控别人，关键边界应该是真诚和不损害对方选择。
- **H26**：开始谈话时用友善的方式，比先发泄情绪更可能得到合作。
- **H27**：别人说话时，脑子里不要只准备下一句反驳，可以先确认自己有没有理解完整。
- **H28**：想纠正别人之前先想一想，自己在相同处境下是不是也可能做出类似选择。
- **H29**：人不一定反对事情本身，可能只是反对被强迫、被忽视或被轻视的感觉。
- **H30**：给人一个值得努力维护的好评价，比反复强调他的缺点更可能改变行为。
- **H31**：冲突时，先放慢语速。
- **H32**：纠正事实前先判断情绪是否已经阻断沟通。紧急或高风险错误要立即澄清；普通分歧可以先确认感受和共同目标，再讨论证据。
- **H33**：每天复盘一次对话：有没有打断、有没有只讲自己、有没有准确理解对方真正担心的事。
- **H34**：关系不是一次谈话建立的，记住对方上次提到的小事，下一次主动问起，才更像真实关心。
- **H35**：有些人表面上要求建议，其实只是想被听见。太快给解决方案反而让他觉得不被理解。
- **H36**：不要吝啬感谢，具体说清楚对方的哪个行动帮助了自己。
- **H37**：人际原则一旦脱离真诚，就可能变成操控技巧。使用倾听、赞美或换位思考时，应尊重对方拒绝的权利，不能把“让别人喜欢自己”置于真实关系和对方利益之上。
- **H38**：称呼名字要自然。记住名字体现关注，反复使用却可能让人感到刻意，尤其是在标准化服务场景中。
- **H39**：线上沟通缺少表情和语气，可以通过先交代目的、减少反问、明确感谢、复述对方观点和避免连续发送情绪化短句来传递友善。
- **H40**：遇到不同意见时，先提出两个真正想了解的问题，再表达自己的判断。提问的目的不是诱导对方承认错误，而是补充自己可能遗漏的事实和立场。连续练习一段时间后，可以用冲突是否减少、理解是否加深来判断这种方法是否有效。

## 二、松果架整理结果

### 松果架 1：理解他人的需要与处境（7 颗松果）

- H02：谈话不能始终围绕自己展开。
- H06：被尊重和被理解的需要并没有因时代改变而消失。
- H07：合作前先理解对方想得到什么。
- H14：推动行动需要连接对方的真实需要。
- H23：面对抱怨，先理解其背后的担忧。
- H28：纠正别人前，先把自己放入相同处境。
- H29：反对可能来自被强迫、忽视或轻视的感受。

### 松果架 2：尊重、认同与保留尊严（7 颗松果）

- H01：批评容易引发自我辩护。
- H04：指出问题前承认自己也可能判断不完整。
- H08：真诚赞美需要具体、真实且不索取回报。
- H09：被否定时，人会本能进入防御状态。
- H17：保全面子可以减少羞耻感对改变的阻碍。
- H18：公开批评更容易触发身份防御。
- H30：给出值得维护的积极评价，有助于推动行为改变。

### 松果架 3：倾听与建立真实连接（7 颗松果）

- H05：记住名字体现了对个体的关注。
- H12：表情会比语言更早传递态度。
- H13：倾听不需要急着展示自己。
- H19：谈论对方兴趣必须建立在真诚之上。

# 本稿需要确认的重点

1. 原始松果是否足够像用户随手收集的信息，而不是提前写好的文章提纲；
2. 每条松果是否只有知识内容，没有额外标题；
3. 信息长度、语气、来源痕迹和完整程度是否足够多样；
4. 松果架标题是否能够准确概括分类后的信息；
5. 暂存栏是否保留了待核实、跨主题和暂时无法判断的信息。
